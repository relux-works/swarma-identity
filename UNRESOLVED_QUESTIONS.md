# Open product decisions

- Live qualification requires the node custodian to select the endpoint, credential-file path and finite read/scan scope. Unit fixtures establish no live-node permission.
- Supporting other Core versions or non-loopback transports requires separate capability and transport qualification.
- Wallet-visible balance requires a separately provisioned and qualified watch-only wallet; it is not implemented or automatically substituted.
- Node lifecycle, name transactions, Nostr/NIP-05 and Link validation require their own interaction contracts. The current raw-read commands establish none of those interfaces.
- `identity show` reports a v3 value problem as a result `reason` (`VALUE_NOT_V3`, `LANDLORD_NOT_V3`) with exit 0, following the v3 identity design. Whether consumers would rather receive a refusal for an agent whose landlord does not resolve is open.
- The design's register/show refusal names (`NAME_MISSING`) and exit codes (1 refusal, 2 retry) differ from this CLI's existing codes (`NAME_NOT_FOUND`, exit 3 refusal, exit 4 retry). `identity show` keeps the existing CLI codes.
- `grant draft` cannot output the grant signing hash, as the design table suggests: the canonical v3 grant contains the consent signature and `landlord_sig`, so the hash exists only after both. `grant sign` therefore runs twice (stage `grant_hash`, then `signed`), and the landlord signs twice. Whether the leads want one landlord review covering both digests (for example a single keyvault prompt) is a signer-UX question outside this CLI.
- **Resolved for the 2026-11-15 seal/anchor producer scope:** `grant anchor` performs `gettxout [txid,vout,true]` before building: at least one confirmation, unspent including mempool, standard P2PKH to the even-y grant key. `grant sign` retains its existing local-ledger guard and does not read the seal on chain. Missing and spent share `SEAL_MISSING_OR_SPENT`, because Core cannot distinguish them through this read. Both new commands return unsigned transaction/PSBT plans only. External signing/broadcast and a verifier's confirmed issuance/closure checks remain separate.
- Seal creation uses the pinned implementation profile's minimum of 100000 atoms and explicit native P2WPKH funding/change with a positive fee rate; LIP-0004 itself gives no numeric seal denomination. Changing this profile or adding automatic wallet funding, transaction signing/broadcast or a live grant verifier requires its own scope. Source-checked RPC fakes do not establish live Core 28.0 wallet/relay qualification.
- Grant refusals use this CLI's exit codes (3 refusal, 2 bad input, 4 retry), not the design's (1 refusal, 2 retry), as `identity show` does.
- **Closed 2026-11-13: G1-K entitlement choice.** The owner's ad-hoc `go build` binary returned `KEYCHAIN_ENTITLEMENT` on the Mac. The owner chose option 1, the Relux Works Developer ID Application identity (team `262RZ595FP`), an explicit App ID, Developer ID provisioning profile and `keychain-access-groups` entitlement in an app bundle. `codesign --verify --strict` passed and the protected `SecItemAdd` succeeded. See `docs/KEYCHAIN.md` and `go run ./cmd/build-keychain-bundle` for the verified recipe. The subsequent protected-item read failure is a separate product defect; acceptance of the fix still requires the owner's dry run (keygen, fixture sign, deletion of both items) with the signed bundle, then the real key.
- G1-K `keychain sign` takes a digest only together with the draft it binds to, so the landlord signs twice per grant (`contract_sha256`, then `grant_signing_hash`). Each signature asks for the selected Keychain authentication separately. The default remains `biometry-current-set`; `biometry-any` and `biometry-or-passcode` are explicit keygen choices, recorded publicly and never applied to an existing item. See `docs/KEYCHAIN.md` for the enrollment/passcode trade-off and rotation by owner-key-signed `name_update`.
- G1-K signer memory hardening (planned migration to libsecp256k1, owner decision 2026-11-13, not scheduled yet). The arithmetic temporaries inside the pinned curve library (secp256k1 v4.4.0 `DoubleNonConst`, `AddNonConst`, `ToAffine`, `FieldVal.Inverse` and `ModNScalar` locals) are not cleared, and Go gives no guarantee of erasing any value, so the clearing of the tool's own buffers is best effort. `docs/KEYCHAIN.md` "Residual memory" accepts this for the one-shot `swarma-keychain` process only. The owner decided to keep the current signer for now; the demo scale does not need more. The path is:
  1. Planned migration: sign through libsecp256k1 via cgo (`secp256k1_schnorrsig_sign32`, `secp256k1_ecdsa_sign`), which clears its own secret intermediates with `secp256k1_memclear`. This adds a C dependency and its build and review. It is not scheduled yet.
  2. Later custody: sign in the keyvault once it is qualified (KEY-MAP K5), so the key never enters this process.

  The migration becomes required before `internal/keysign` is used in any long-running process.

- Keychain access-policy qualification: public Security APIs do not expose the native ACL flags for independent readback. Signing reports this limit and checks authenticated policy metadata; metadata consistency does not establish actual flag equivalence. Hosted macOS CI covers flag construction and a file-keychain metadata round trip without biometry. Actual Touch ID/passcode/password and enrollment-change semantics for each policy still require the owner-signed hardware dry run.

- Trust-contract `/2` depth-one re-delegation, child certification, notary history and executor admission remain outside the depth-zero slice (LIP-0014 at spec 0.1.48). The parser can check child syntax, but issuance and offline signature verification refuse children as `CONTRACT_DEPTH`. A future Mac Keychain `/2` adapter must display all fifteen members and exact scope bytes before it may sign; its current `/1` adapter refuses `/2` drafts. Task-specific unknown/duplicate-member and depth refusal codes differ from the draft LIP and are documented in `docs/GRANT.md`; broad LIP-0014 conformance remains unclaimed.
