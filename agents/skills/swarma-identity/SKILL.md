# Swarma Identity

Use the repository-built `swarma-identity` CLI. Read [the CLI contract](../../../docs/CLI.md) for exact schemas and error codes. Build instructions are in [README](../../../README.md).

- Offline derivation: `swarma-identity address derive --request FILE --json`. Supply only a public xpub/tpub, explicit network, relative non-hardened path and finite range. It needs no node, relay or signer.
- Health: `swarma-identity node health --config FILE --json`.
- Raw name: `swarma-identity name show --config FILE --request FILE --json`. Exact value bytes are hex; this establishes no Link or identity authority.
- v3 identity: `swarma-identity identity show --config FILE --request FILE --json`. Gives `role` landlord, agent or none with keys and the agent's resolved landlord. Treat any present `reason` (`VALUE_NOT_V3`, `LANDLORD_NOT_V3`) as "not a usable v3 identity"; it is not a grant check.
- Current UTXOs: `swarma-identity balance watch --mode utxo-scan --config FILE --request FILE --json`. Require the node custodian's authorization to occupy its shared scan resource. Supply exactly branches `[0,1]`, P2WPKH and an explicit range of at most 1000 indices per branch.
- Unsigned profile: `swarma-identity nostr profile-prepare --request FILE --json`. Supply an explicit public x-only key, timestamp, kind0, ordered tags and JSON-object content text under the exact schema and limits in the CLI contract. The result includes canonical bytes as a UTF-8 string and an unsigned event, never a signature.
- Public profile verification: `swarma-identity nostr profile-verify --request FILE --json`. Supply the complete already-signed public event under the verification schema. Success binds its canonical fields, id and BIP-340 signature only; it establishes no relay publication, ownership, freshness, domain or identity authority.

- Trust grant, two-phase (see [the grant contract](../../../docs/GRANT.md)): `grant draft --config FILE --request FILE --seal-ledger ABS_FILE --json` builds the LIP-0013 contract and v3 fields and lists the digests to sign in `to_sign`; the grantee signs `consent_event_id` with its own signer; `grant consent --request FILE --json` verifies that consent; the landlord signs `contract_sha256`; `grant sign --config FILE --request FILE --seal-ledger ABS_FILE --json` without `grant_sig` returns `grant_signing_hash`; the landlord signs it; `grant sign` with `grant_sig` returns `signed_grant`, `grant_id` and `commitment`. Hand each signer the digest together with the exact public bytes it commits to, so the signer can render them and recompute the digest before signing: `consent_template` (NIP-01 serialization, giving `consent_event_id`) to the grantee's signer, `contract_b64` (SHA-256 gives `contract_sha256`) and `grant_b64` (the canonical unsigned grant behind `grant_signing_hash`) to the landlord's. Take back only public signatures. Never give this CLI a private key, a key file or a Keychain item; it has no option for one. The grant is not live until external publication and confirmed verification on the verifier's node; a live verify command is still planned. If draft or sign refuses `LEDGER_FILE` with the message naming `grant ledger-recover`, a temporary file from an interrupted update may hold earlier seals: run `grant ledger-recover --seal-ledger ABS_FILE --json` (offline), which merges it back or refuses (`LEDGER_RECOVERY_CONFLICT`, or `LEDGER_FILE` for a file it cannot classify); never delete the `.<ledger>.tmp-*` file by hand.

- Unsigned grant transactions: `grant seal --config FILE --request FILE --json` builds one even-y grant-key P2PKH seal (profile minimum 100000 atoms) and separate funding change; `grant anchor` with the same flags takes exact `signed_grant_b64`, `contract_b64` and explicit public funding, checks the current issuer and confirmed/unspent seal using `gettxout [txid,vout,true]`, and builds the exact LIP-0005 frame. Both always return `dry_run:true`, unsigned wire bytes and PSBTv0. Use only explicitly supplied native P2WPKH funding pins/full parents and fee rate, following GRANT.md. No wallet is selected, no key is handled and no signing/broadcast flag exists. Treat `SEAL_MISSING_OR_SPENT`, `SEAL_UNCONFIRMED`, `SEAL_SCRIPT_TYPE`, `SEAL_KEY_MISMATCH` and any other refusal as no plan. The pre-check is not atomic or a live-grant verdict; external wallet review, signing, publication and confirmed verification remain required. Draft/sign retain their local-ledger guard.

- V3 seal lifecycle: follow [the operator runbook](../../../docs/SEAL.md). All four commands require explicit `--network NETWORK --issuer-key EXPECTED_XONLY_KEY`; neither defaults. Use the operator trusted issuance key, not a key copied from an untrusted request. `seal plan --network regtest --issuer-key EXPECTED_XONLY_KEY --request FILE --journal ABS_FILE --json` reconstructs the exact seal already named by the signed v3 grant and writes its public per-grant journal; it does not change a grant or choose a wallet. Only `swarma-keychain seal sign --network regtest --issuer-key EXPECTED_XONLY_KEY --journal ABS_FILE --label LABEL --json` signs, through the existing terminal, exact SIGN approval and native authentication. `seal broadcast --network regtest --issuer-key EXPECTED_XONLY_KEY --journal ABS_FILE --config READ_FILE --broadcast-config WRITE_FILE --json` uses the verifier RPC user for reads and separate explicit broadcast authority for one durable attempt; every funding parent must have present integer confirmations >= 1 or it refuses `SEAL_FUNDING_UNCONFIRMED` before acceptance/attempt writes. A repeated broadcast call is a local report, never another send. For `needs_reconciliation:true`, missing responses or recovery fences, preserve the journal and use `seal observe --network regtest --issuer-key EXPECTED_XONLY_KEY --journal ABS_FILE --config READ_FILE --json` for read-only reconciliation; never reset or copy the journal to get another attempt. Network main additionally requires both `--allow-mainnet` and separate `--confirm-mainnet MAINNET` on every invocation; these never replace the signer SIGN approval. This is the v3 P2PKH grant seal, not a v4/framework contract seal or a single-use two-branch seal. Minimal v3 contracts need no contract seal at spec v0.1.61, with C12 versus C8 still open. Current qualification is regtest fixtures only; production remains operator-owned.

Both Nostr commands are offline, accept no config or signing flag and select no ambient key or timestamp. Content text and tag order are preserved. Check `EVENT_ID_MISMATCH` and `INVALID_SIGNATURE` as refusals with no partial result, never as `valid:false` successes. Keep public input files explicit; do not supply private keys or obtain a signature through this interface.

Online calls require an explicitly selected loopback Core 28.0 node and an existing owner-only credential file. Never inspect or paste credentials, place them in argv, discover another wallet or replace missing authorization with a test fixture. Keep account-specific request/result files in ignored local custody.

Check `ok` and the process exit code before using a result. A matched UTXO total is confirmed-only for the explicit range, not the entire xpub or a spendable balance; coinbase outputs can be immature. Read the returned coverage and observed tip. Missing/expired names and unavailable/unsynced nodes are refusals, not zero funds or absent identity.

For SCAN_BUSY or SNAPSHOT_CHANGED, report the refusal; the tool does not retry. SCAN_UNCERTAIN means the node may still be scanning: do not claim it stopped or launch a blind retry. Never send abort; this interface has no per-caller ownership token. No wallet import/rescan, general transaction signing/broadcast, node lifecycle, Nostr publication or plugin registration interface exists in this slice. The bounded seal lifecycle above is the only transaction-signing/broadcast exception; route other requirements to their separately agreed implementations.
